Nachdem ich die Journal‑Funktion zu diesem Playground hinzugefügt hatte, ging
die gesamte Seite auf meinem Shared Hosting offline.
Was folgte, war eine Debugging‑Reise, die mit einer deutlich einfacheren und
zuverlässigeren Deployment‑Lösung endete → zurück zu den Wurzeln.

## Das Problem

Die App läuft auf Novatrend Shared Hosting mit cPanel, das CloudLinux verwendet,
um Ressourcenlimits durchzusetzen.
Nachdem ich die Journal‑Funktion hochgeladen hatte, begann die Node.js‑App
NprocF (Number of Processes Faults) zu erreichen — das bedeutet,
sie überschritt das Limit von 100 Prozessen, das auf Shared Hosting erlaubt ist.

Der cPanel‑Fehler war eindeutig: „Unable to fork — User has reached resource
limits“. Der Next.js‑Standalone‑Server konnte gar nicht mehr starten.

## Debugging‑Reise

### Versuch 1: Abhängigkeiten reduzieren

Erster Verdacht:  <a href="https://www.npmjs.com/package/fast-glob" target="_blank" rel="noopener noreferrer">`fast-glob`</a>, das verwendet wird, um App‑ und Journal‑MDX‑Dateien während des Builds zu entdecken, könnte zur Laufzeit Child‑Prozesse starten.
ch ersetzte es durch das in Node integrierte <a href="https://www.geeksforgeeks.org/node-js/node-js-fs-readdirsync-method/" target="_blank" rel="noopener noreferrer">`fs.readdirSync`</a> — weniger Abhängigkeiten, keine Child‑Prozesse.
Ein Blick auf die Build‑Ausgabe zeigte jedoch, dass alle Seiten bereits mit  ○ 
(Static) markiert waren.
Der Austausch von glob war zwar eine gute Aufräummassnahme, aber nicht die
Ursache — diese Funktionen liefen nur während des Builds, nicht auf dem Server.

### Versuch 2: Das Standalone‑Bundle verschlanken

Als Nächstes bemerkte ich, dass  typescript  (20 MB) und andere reine
Build‑Pakete in  dependencies  statt in  devDependencies  standen. Nachdem ich
sie verschoben und  outputFileTracingExcludes  hinzugefügt hatte, schrumpfte der
Standalone‑Output von 59 MB auf 23 MB — eine Reduktion um 61%.

Trotzdem trat derselbe Fehler auf. Der Node.js‑Prozess konnte innerhalb des
Prozesslimits gar nicht erst starten.

### Die Erkenntnis

Das Problem war keine bestimmte Abhängigkeit und auch keine besonders schwere
Seite — es war der Next.js‑Standalone‑Server selbst. Selbst ein minimaler
Node.js‑ + Next.js‑Server benötigt mehrere Prozesse zum Starten (V8, Garbage
Collector, Worker‑Threads). Auf einem Shared Host mit einem 100‑Prozess‑Limit,
das sich alle deine Websites teilen, ist das einfach zu viel.

## Die Lösung

Die entscheidende Erkenntnis: Jede einzelne Seite in dieser App ist statisch. Es gibt keine API‑Routes, kein Middleware, kein Server‑Side Rendering, und <a href="https://www.supabase.com" target="_blank" rel="noopener noreferrer">`Supabase`</a> läuft komplett im Browser. Ich brauche überhaupt keinen Server.
Der Wechsel zu  output: 'export'  in der Next.js‑Konfiguration erzeugt reine
HTML‑, CSS‑ und JavaScript‑Dateien — direkt von Apache ausgeliefert, ohne
jegliche Node.js‑Beteiligung.

```javascript
// next.config.mjs — the one-line fix
const nextConfig = {
  output: 'export',        // was: 'standalone'
  images: { unoptimized: true },
}
```

The results were dramatic:

| | Standalone | Static Export |
|---|---|---|
| Deploy size | 107 MB (3511 files) | ~2 MB |
| Node.js process | Yes | No |
| NprocF risk | High | Zero |
| Server | Passenger + Node.js | Apache (default) |

Ein einfaches  deploy.sh  kopiert jetzt nur noch den  out/ ‑Ordner und eine
 .htaccess ‑Datei (für gzip‑Kompression und Browser‑Caching) in ein Zip‑Archiv.
Hochladen in cPanel, fertig — kein App‑Neustart, kein Passenger, kein Node.js.

## Key Takeaway

Wenn alle deine Seiten statisch sind, brauchst du keinen Server. Bevor du zu
 output: 'standalone'  greifst, prüfe, ob  output: 'export'  deinen
Anwendungsfall abdeckt. Für eine Website ohne API‑Routes, ohne SSR und nur mit
clientseitigem Daten‑Fetching ist Static Export einfacher, schneller und
deutlich kompatibler mit Shared‑Hosting‑Umgebungen.
